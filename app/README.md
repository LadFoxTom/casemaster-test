# Mini CRM — cms-vercel demo

A tiny CaseMaster application that runs on Vercel against a Neon
Postgres database. It exists to prove the runtime end-to-end: parse
`.cms` files, register BOs, render pages, talk to the DB, and serve
auto-generated CRUD UIs.

## What's in here

```
app/
├── bo/crm/
│   ├── contact.cms       — Contact BO (table: crm_contact)
│   └── task.cms          — Task BO    (table: crm_task, FK → contact)
└── page/
    ├── setup.cms         — one-shot DDL bootstrap + seed
    ├── home.cms          — dashboard: counts + latest 5 of each
    ├── ping.cms          — DB connectivity check (text/plain)
    └── hello.cms         — qualifier-rendered HTML demo
```

Two BOs, two new pages, two demo pages from the runtime — that's the
whole app.

## First-run flow

1. Configure `DATABASE_URL` in `.env.local` (locally) or in the Vercel
   project's *Settings → Environment Variables* (production).
2. Visit `/page/foo/f/setup` once. It runs `CREATE TABLE IF NOT EXISTS`
   for `crm_contact` and `crm_task`, then seeds three contacts and five
   tasks if `crm_contact` is empty. Idempotent.
3. Visit `/page/foo/f/home` for the dashboard.

## Routes

| Path                              | What it does                                          |
|-----------------------------------|-------------------------------------------------------|
| `/page/foo/f/setup`               | Create schema + seed sample data (idempotent)         |
| `/page/foo/f/home`                | Dashboard — counts, latest contacts, latest tasks     |
| `/page/foo/f/ping`                | `ok N` — proves the Postgres pool is wired            |
| `/page/foo/f/hello`               | Styled HTML through the `<@page/container>` path      |
| `/maintenance/crm/contact`        | Auto-CRUD list / new / edit / delete for contacts     |
| `/maintenance/crm/task`           | Auto-CRUD list / new / edit / delete for tasks        |
| `/?diag=1`                        | Registry diagnostics (loaded fns, app dir, DB flag)   |

The `/maintenance/<bo>` pages are generated by the runtime from the BO
declarations — there is no UI code in this app for them.

## Schema

```sql
CREATE TABLE crm_contact (
  id          BIGSERIAL    PRIMARY KEY,
  full_name   VARCHAR(120) NOT NULL,
  email       VARCHAR(200),
  company     VARCHAR(120),
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE crm_task (
  id          BIGSERIAL    PRIMARY KEY,
  contact_id  BIGINT       REFERENCES crm_contact(id) ON DELETE SET NULL,
  title       VARCHAR(200) NOT NULL,
  status      VARCHAR(20)  NOT NULL DEFAULT 'open',
  due_date    DATE,
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

The same DDL is emitted by `app/page/setup.cms` via `sql.execute`, so
you don't need to run it manually.

## What this demo exercises in the runtime

- **Loader** — multi-segment BO paths (`crm/contact`, `crm/task`).
- **BO registry** — `<@bo>` extraction with `attributes`, `attributeGroups.list`, `foreignKey`.
- **Auto-CRUD** — `/maintenance/<bo>` list / new / edit / delete.
- **Iterator** — `iterate iterator.ofEntity(<@iterator/entity entity:'crm/task' orderBy:'-id'>) rows: 5`.
- **Raw SQL** — `iterate sql.fetch(...)` for an aggregate count, `sql.execute(...)` for DDL + bulk inserts.
- **Page rendering** — `response.setContentType / write / flush / end` with built-up HTML.
